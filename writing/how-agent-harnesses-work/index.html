How an agent harness works

Two teams can use the same model and build very different agents, because most of an agent isn't the model. LangChain puts it as agent = model + harness, where the harness is every piece of code, configuration and execution logic that isn't the model. Scroll through its four jobs. This is the first of three explainers, with loops and graphs.

  1. 1

    Take the model out of the diagram

    A model turns text into text. It can't read a file, call an API, remember yesterday or ask for permission. Each of those is code around the model, and all of it together is the harness: the system prompt, the tools, the workspace, the memory, the permission rules and the logs.

  2. 2

    What goes in: context

    Before every call the harness decides what goes into the context window: instructions, tool descriptions, retrieved documents, memory and the state of the task. The model knows only that. In my research agent, the citations come from the search tool, not from the model, so a cited source always exists.

  3. 3

    What comes out: actions, with permissions

    A tool call is a request; the harness decides whether it runs. Searches run in a sandbox, file access stays inside the workspace, and risky actions wait for approval. In my prompt-injection lab, an approval gate on email stopped all 12 hijacking attempts, although the model tried 5 times: it doesn't depend on the model obeying.

  4. 4

    What survives: state between sessions

    A context window ends; long tasks don't. Anthropic found that compaction alone wasn't enough for coding agents that work across many sessions. Their harness has a first session write a feature list, a progress file and an initial git commit; every later session reads them, works on one feature, and commits.

  5. 5

    What you can see: traces and checks

    The harness logs every model call, tool input and output, tokens and time, and runs deterministic checks such as tests or a linter. Without that trace you can't tell whether a run failed because of the model, or because the harness gave it the wrong context or a broken tool.

In short

  • Before blaming the model or switching to a bigger one, look at what the harness showed it and what it let it do. Stale context, vague tool descriptions and missing exit conditions look like model mistakes.
  • Least privilege applies to agents. Of the four defenses in my injection lab, the approval gate was the only one that brought hijacking to zero, and it was code, not a prompt.
  • More isn't better: each extra tool is one more choice the model can get wrong, and each extra document is more text to get lost in.
  • The vocabulary is new and loosely used. The definition that holds up is the simple one: everything that isn't the model. The loops that check its work are covered in How agent loops work.
