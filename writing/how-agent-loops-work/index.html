How agent loops work: the loops around the loop

Every tool-using agent already runs a loop: call the model, run the tools it asks for, feed back the results, repeat. Loop engineering, a name that caught on in 2026, is designing the loops around that one: what checks the work, what starts a run, what improves the agent over time, and what makes each loop stop. This is the second of three explainers, after the harness.

  1. 1

    The agent loop

    The model gets the task and either answers or asks for tools. The harness runs the tools, appends the results, and calls the model again. The loop ends on a final answer or at a turn limit: OpenAI's Agents SDK raises an error once max_turns is exceeded, rather than letting it run on.

  2. 2

    The verification loop

    A grader checks the output against something outside the model: tests, a schema, whether the citations exist, or a rubric. A failure goes back with feedback and the agent tries again. In my research agent the grader is a critic that reads the findings and asks follow-up questions; it sent 26 of 100 benchmark questions back for a second round.

  3. 3

    Stop on evidence, not confidence

    Every loop needs a rule for stopping: the check passes, a maximum number of rounds, a budget, or a hand-off to a person. “The agent says it's done” isn't one; Anthropic saw long-running coding agents declare projects finished too early. My research loop stops when the critic is satisfied, has no follow-ups, or after two rounds, so a strict critic can't loop forever.

  4. 4

    Loops started by events

    An agent doesn't have to wait for someone to type. A schedule, a webhook or a new document can start each run, and the agent becomes one component running inside a larger system, which is why its stop rules and budgets matter more.

  5. 5

    The improvement loop

    Read the traces of past runs, find where they fail, change the harness (a prompt, a tool, a limit) and run the same test set again. LangChain calls this hill climbing. Without a fixed test set, a version that feels better can be worse.

In short

  • Loops cost calls. My agent used 5.7 model calls per question against 1 for a single call, for 86% correct against 74% on 100 multi-hop questions. Add a loop where a failure costs more than the check.
  • Prefer checks the model can't talk its way past: tests, schemas, does the cited source exist. A grader that is the same model can share the writer's blind spots, so give it a separate context at least.
  • Order loops by cost: try the cheap path first and loop only when it fails. On my benchmark, a single call first and the agent only when the call said the sources were insufficient would have scored 87% at about 2.1 calls per question. That's simulated after the fact, so it's a hypothesis to test, not a result.
  • The ideas are older than the name: Anthropic described the evaluator-optimizer loop and iteration limits in 2024. Where the loops sit, and in what order, is the subject of How agent graphs work.
