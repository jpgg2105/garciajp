# /for pages

One page per company, at garciajp.com/for/<slug>/. Each shows a tailored, animated sketch of how Juan Pablo
would solve a real problem that company has, plus one small interactive demo. They are not generated by the
root build.py, carry `noindex`, and are not in the sitemap.

## Add a page
1. In `pages/`, copy an existing set and rename: `<slug>.json` (title, desc, eyebrow, h1, lede, stage, flow),
   `<slug>.body.html` (demo section + "How I would build it" + "What I would check first"), `<slug>.js` (demo code).
   - `flow.nodes`: `c` = column along the flow (0 to 5 max), `r` = row (0 to 2 max). Labels short (about 18 chars),
     subs about 24 chars. `tag` is one of source, data, code, model, LLM, edge, db, queue, tool, PR, out, traffic.
   - `flow.edges`: `{a, b}`; one optional `{back: true, label}` feedback edge. Avoid edges that cross other boxes.
   - `flow.steps`: 5 to 7 steps, each `{t, d, on: [node ids], go: ["a>b"]}`.
2. `python for/_src/build_for.py <slug>` writes `for/<slug>/index.html`.
3. `python for/_src/shot.py /tmp/shots <slug>` serves the repo and saves desktop and phone screenshots. Look once, fix.
4. Commit and push to main. GitHub Pages publishes in about a minute.

## Writing rules for pages and emails
- No em dashes, en dashes, semicolons or double quotes. Avoid colons in prose. No stock AI phrasing.
- Ground the problem in something the company says publicly (help center, job post, site copy) and say where it came from.
- Every made-up number is labeled as an example. Never claim inside knowledge or results Juan Pablo did not get.
- No company logos or branding. The page is clearly Juan Pablo's own sketch.
- `python for/_src/check_email.py email.txt` before sending any email.
