A sketch for HIFI Labs

Drop day, when every fan shows up in the same minute

An artist posts the link and most of the day's traffic lands in the first few minutes. On Firebase that is a known pain. Google's guidance puts a single document at about one sustained write per second, and says a new collection should start around 500 operations per second and grow from there. This is the setup I would put in front of the next activation, on the stack you already use.

Launch simulator

A simple model of the first ten minutes. Fans arrive front loaded, 40 percent in the first minute, and each one makes one write. Move the slider and switch between sending everyone straight to Firestore and using the waiting room.

A model, not a measurement

Grey is fans arriving per second. Teal is writes reaching Firestore. The dashed line is the 500 per second starting rate.

How I would build it

  • A Cloudflare Worker waiting room with signed, short lived tokens, deployed where you already deploy.
  • A load test the week before that replays the first ten minutes at full size against a staging project, with k6.
  • One document per fan and a count query rolled into a single total, instead of a shared counter.
  • Cloud Tasks for anything slow or third party, with retries and idempotency keys so a retry never double claims.

What I would check first

  • What broke on the last big activation, if anything, and where the time went.
  • Which actions have to feel instant for the fan and which can finish a few seconds later.
  • Whether drops have a fixed supply, which changes how the line should be ordered.

I have shipped more on Postgres and FastAPI than on Firebase, so the limits on this page come from Google's published guidance, not from a launch I ran.
